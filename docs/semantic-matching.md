# 拾梦 Gleam · 语义匹配设计文档

> 状态：v1 定稿。除标注「已实现」外，其余为待落地项。
> 前提修正：DeepSeek 没有 embedding API。embedding 用 SiliconFlow 的 BGE-M3（1024 维，OpenAI 兼容，当前免费），LLM 结构化抽取用 deepseek-chat。这是现状，也是定稿方案。

---

## 1. 相似度定义：混合打分，向量为主、意象为辅

**结论：纯 embedding 余弦不够，但也不需要复杂的多维结构化。用「向量余弦 × 意象重合」两项混合。**

纯余弦的问题在梦境语料上被放大：中文梦境记录短（多数 <100 字）、口语碎片化，BGE-M3 在这种文本上区分度中等——实测「坠入海」vs「深海下沉」只有 0.67，而两段语义无关的梦也常在 0.45–0.55 徘徊。余弦只能回答"文本像不像"，回答不了产品真正要的"是不是同一个梦"——后者由核心意象决定（都梦见坠落、都梦见牙齿掉了），哪怕叙述完全不同。

反方向，全套结构化维度（意象/情绪/场景/人物关系各自打分再加权）是过度设计：每个维度都要 LLM 抽取和对齐，误差相乘，权重没有数据可调，冷启动期纯属拍脑袋。**我们已经有意象抽取管线（`dream_motifs` 表，DeepSeek 抽 2–6 个带权重的意象），直接用它做第二信号，零新增成本。**

**打分公式（定稿）：**

```
score = 0.7 × cosine(e_a, e_b) + 0.3 × motif_overlap(a, b)

motif_overlap = Σ min(w_ai, w_bi) / Σ max(w_ai, w_bi)   # 加权 Jaccard，i 遍历两梦意象并集
```

- 0.7/0.3 的理由：向量承载全文语义，是主信号；意象是"同梦"的判据放大器。意象只有 2–6 个，重合是稀疏事件——一旦重合（尤其"坠落""牙齿"这类高辨识意象），0.3 的权重足以把一对梦从弱匹配推进强匹配区间；不重合时也不至于杀死一对文本高度相似的梦。
- 情绪不进公式，但做**否决项**：`emotion_score` 同号或任一为空 → 通过；一个 >0.5 一个 <-0.5（一个平静一个惊惧）→ score 打 8 折。同一意象截然相反的体验不该被推成"同一个梦"。
- 工程形态：pgvector 先按余弦取 top-50 候选（省算力），应用层对候选算 motif_overlap 出终分。不要试图在 SQL 里做加权 Jaccard。

## 2. 阈值与分层

**结论：两档，强匹配 ≥ 0.72，弱匹配 0.58–0.72。低于 0.58 静默。**

数值来源：现库实测同主题异表述对在 0.65–0.70（纯余弦），叠加意象重合后同梦对普遍上探 0.75+；0.58 下限对应现在代码里的 `MATCH_THRESHOLD = 0.6` 微调。**这两个数是初始值不是真理，上线后按误报率调：强匹配的验收标准是用户看到对方的梦会说"这就是我的梦"，弱匹配的标准是"有点像，挺妙的"。每周人工抽 20 对读一遍，比任何离线指标都准。**

| | 强匹配（同梦） | 弱匹配（相似意象） |
|---|---|---|
| 分数 | ≥ 0.72 | 0.58 – 0.72 |
| 文案 | 「今晚，有人和你梦见了同一件事。」 | 「有 N 个梦，和你的梦隔着相似的影子。」 |
| 呈现 | 广场顶部匹配横幅 + 通知，可发起 48h 匿名对话 | 只在梦境详情页尾部安静显示一行，无通知 |
| 数量 | 单播感（"有人"），最多显示 1 对 | 聚合数字，不列具体内容 |

关键取舍：**48h 对话入口只给强匹配。** 弱匹配开对话会稀释"我们做了同一个梦"的击中感，而这个击中感是整个产品的心跳。弱匹配的价值是让用户知道"梦的世界里我不孤独"，到此为止。

## 3. 冷启动

三个方案，全部做过权衡：

- **A. 跨时间匹配**：匹配窗口从 24h 放宽到全历史。文案改为「三个月前，有人梦见过和你同一件事」。优点是零内容成本、完全真实；缺点是失去"今晚"的共时感。
- **B. 官方种子梦境**：文学作品与公开梦境档案灌 300 条（PRD 的"梦境档案馆"）。优点是广场不荒；缺点是种子梦不能进对话匹配（对面没有人），只能撑弱匹配和广场，且必须标注来源否则是欺骗。
- **C. 遥远回响**：匹配不到时降阈值到 0.5 找"最不坏"的一条推给用户。**否决**——低质匹配第一次让用户说"这哪里像了"，产品的魔法就死了。宁可沉默不可硬凑。

**拍板：A 为主，B 为辅。** 跨时间匹配是产品级正确而不只是冷启动补丁：梦的共鸣本来就不该被 24 小时切断，"三个月前有个人梦见过同样的事"甚至比"今晚"更动人。实现上把 `count_recent_similar` 的时间窗做成参数：先找 24h（文案"今晚"），找不到退 30 天（"这个月"），再退全量（"曾经"）。种子库只服务广场信息流和第 1 个梦的全站意象对比（已实现），明确标注「梦境档案馆」，永不进对话匹配。

## 4. 触发时机与频率

**结论：写入时同步匹配 + 每晚一次批量补扫。不做常驻实时。**

- **写入时**（已实现雏形）：新梦 embedding 落库后立即跑一次匹配，命中强匹配 → 给**双方**各写一条应用内通知。刚记完梦的人正处在最想被回应的时刻，这一次匹配的转化价值最高。
- **每晚批量**（pg_cron 03:00）：扫过去 24h 的梦互相补配。作用有二：补上"我先记、对方后记"时我方错过的通知；跨时间匹配（§3）也挂在这个任务里，摊平计算。
- **通知策略，三条铁律**：
  1. 应用内通知优先（打开 App 首屏横幅，已实现），Web Push 只发强匹配，每用户**每天最多 1 条**；
  2. 推送时间窗锁定 **20:00–23:00**（睡前，也是记梦产品的天然活跃时段）——凌晨匹配到了也压到晚上发，绝不在深夜震动用户的手机，这是深夜模式价值观的延伸；
  3. 未读不叠加：已有未读匹配通知就不再写新的（已实现）。

## 5. 反滥用

匿名 + 梦境私密性 = 钓鱼者的理想温室（编"性梦""孤独梦"钓匹配，进 48h 对话后骚扰）。三档社交机制管的是"表达成本"，管不住恶意，需要四层：

1. **入口审核**（已实现，需持续加词）：投放与对话消息全过机审；自伤内容让路逻辑优先于一切。
2. **对话内举报 + 单方即时关闭**（P0 待做）：48h 对话页加两个按钮——「关闭对话」（单方点击立即销毁，不通知对方原因）和「举报」（快照最近 20 条消息进 `reports` 表供人工复核，然后销毁）。匿名对话里用户唯一的自保手段就是"随时离开且不留痕"，这必须是一等公民。
3. **行为限速**：每用户每天最多发起 3 次匹配对话、每梦最多被同一人举报计 1 次；被 2 个不同用户举报 → 自动禁言对话功能 7 天，被 3 人举报 → 该账号所有公开内容下架待人工。阈值从严，匿名社区的信任崩一次就没了。
4. **钓鱼文本的结构性防御**：匹配只对"梦"生效，而梦要过意象抽取——纯挑逗文本抽不出正经梦境意象（意象数 <2 的梦不进匹配池，现有 `tooShort` 逻辑扩展一条）。这不是完美过滤，但把钓鱼成本从"发一句话"抬高到"编一个完整的梦"。

## 6. pgvector 实现

**现状（已建）**：`dreams.embedding vector(1024)`（BGE-M3）+ HNSW 索引 + `match_dreams` / `count_recent_similar` / `recent_similar_dreams` 三个 SQL 函数，`dream_motifs(dream_id, motif_id, weight)`。

**索引拍板：HNSW，不用 IVFFlat。** 理由：IVFFlat 需要先有数据再建索引（列表中心从数据聚类而来），冷启动期数据分布天天变，要反复重建；HNSW 增量插入友好、召回率更高，代价是内存略大——万级梦境规模下这个代价可以忽略。参数用默认（m=16, ef_construction=64），十万条以内不用调。

```sql
-- 已建
create index dreams_embedding_idx on dreams using hnsw (embedding vector_cosine_ops);

-- 待加：混合打分的候选查询（应用层再算 motif_overlap 出终分）
create or replace function match_candidates(
  query_embedding vector(1024),
  self_dream uuid,
  self_user uuid,
  since timestamptz,          -- 时间窗参数化：24h / 30d / '-infinity'
  candidate_count int default 50
) returns table (dream_id uuid, user_id uuid, cosine real)
language sql stable as $$
  select d.id, d.user_id,
         (1 - (d.embedding <=> query_embedding))::real
  from dreams d
  where d.id <> self_dream
    and d.user_id is distinct from self_user
    and d.embedding is not null
    and d.created_at >= since
    and d.is_night_mode = false          -- 深夜模式的梦不进匹配池
  order by d.embedding <=> query_embedding
  limit candidate_count;
$$;
```

应用层伪码：

```ts
const cands = await rpc("match_candidates", {...});
const scored = cands.map(c => ({
  ...c,
  score: 0.7 * c.cosine + 0.3 * weightedJaccard(myMotifs, motifsOf(c.dream_id)),
})).map(applyEmotionVeto);
const strong = scored.filter(s => s.score >= 0.72);
const weak   = scored.filter(s => s.score >= 0.58 && s.score < 0.72);
```

维度说明：1024 是 BGE-M3 固定输出，够用且省一半存储（对比 1536）。**换 embedding 模型 = 全量重算 + 改列定义，是大手术，上线后非必要不换。**

## 7. 成本估算（10,000 DAU，每人每天 1 条梦）

单价（2026 年中）：deepseek-chat 输入 ¥2/M tokens、输出 ¥8/M（缓存命中输入 ¥0.5/M，系统提示词可缓存）；BGE-M3 在 SiliconFlow **免费**，SenseVoice 转写免费额度内。

每条梦的 LLM 调用：意象抽取（必发）约 0.5k 入 + 0.15k 出；AI 基线解读（仅投放广场的梦，按 20% 投放率）约 0.6k 入 + 0.3k 出；续写故事（用户主动，按 10% 点击）约 0.7k 入 + 1.5k 出。

| 项目 | 日用量 | 日成本 |
|---|---|---|
| 意象抽取 10k 次 | 5M 入 / 1.5M 出 | ≈ ¥22 |
| 基线解读 2k 次 | 1.2M 入 / 0.6M 出 | ≈ ¥7 |
| 续写故事 1k 次 | 0.7M 入 / 1.5M 出 | ≈ ¥13 |
| embedding 10k 次 | — | ¥0 |
| 匹配计算（pgvector） | 数据库内 | ¥0（含在 Supabase 套餐） |
| **合计** | | **≈ ¥42/天，¥1,300/月** |

结论：**万 DAU 量级下匹配管线的 AI 成本约 ¥0.004/用户/天，可以忽略。** 真正的成本悬崖在图像生成（约 ¥0.2–0.4/张，若 50% 的梦生成一张即 ¥2,000+/天，是 LLM 的 50 倍）——这就是 PRD 里星光经济作为"成本阀"针对的对象，与匹配管线无关。系统提示词全部固定以吃 DeepSeek 缓存价，可再降 30%。
